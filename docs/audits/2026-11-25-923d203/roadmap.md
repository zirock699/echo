## 1. Capture and private snapshots

**Scope.** Start with cancelling an outstanding legacy microphone request when its UI exits. Then validate restored and API snapshots at likely trust boundaries and keep imported values out of markup construction. Confirm a stable opaque owner identity before defining unowned-cache recovery and Mirror partition behavior. Treat dev-server asset scoping as a separate small change if preview needs require it. See `PRIV-01` through `PRIV-04` in the [register](findings.md).

**Approach and risk.** Reuse the existing cancellation pattern. Keep legacy compatible data only after explicit shape and safe-value normalization. Do not silently assign an old cache to a different account. Test host security headers and identity at the authorised release stage. Risks are breaking valid old exports, interrupting offline recovery, or taking away a supported recording mode.

**Acceptance.** A delayed simulated permission after Cancel, route leave or hidden state leaves no media track or hidden result. Valid legacy exports round-trip and unsafe structure is rejected before any durable write. Legacy-render delimiters remain literal. Two synthetic signed-in owners in one browser profile can neither see nor submit each other's cache or attempts. Same-owner offline recovery and current owner isolation still work. Independent Reviewer verifies lifecycle, owner policy, compatibility and safe output evidence.

**Verified locally, 25 November 2026.** The recorder releases simulated late microphone grants on Close, Back and hide. The state and media APIs bind writes to the authenticated account before processing them. Browser cache, history and Mirror attempts are scoped by owner, and stale callbacks cannot publish in another account. Cold offline starts leave private data locked. A previously verified open tab can keep working through a network outage and pending work returns after same-owner verification. Unbound legacy records remain intact. A user-owned JSON backup is the portable recovery route. The development preview serves only app assets and the explicit QA fixtures.

## 2. Library and media integrity

**Scope.** Share one lesson deletion operation. Reconcile course/collection membership, progress references and source assets in the same domain operation. Make keep/replace/remove intent explicit for each optional asset. Keep operational deletion intent out of portable restore data and recheck accepted references before cleanup. See `DATA-01` and `DATA-02`.

**Approach and risk.** Preserve old media until a valid snapshot establishes it is unused. Use a revision-aware policy with an explicit recovery or grace period where feasible. Avoid a table redesign. Be clear about metadata-only backups. Risks are premature deletion, orphan growth and accidentally resetting existing lesson identity or progress.

**Acceptance.** Player and Library deletion leave identical consistent course state, including Continue and artwork. Replacement with missing/failed optional art preserves prior artwork. Accepted references survive interrupted save, restore, conflicts and repeated cleanup with synthetic assets. Intentionally removed and unreferenced assets can be retired under the policy. Independent Reviewer verifies current/previous snapshot, restore and two-context cases with the Data Engineer.

**Verified locally, 25 November 2026.** Player and Library share one deletion operation. Surviving progress and shared media stay intact, stale course entries no longer block Continue, and optional ZIP artwork and captions survive absent or failed replacements. Cleanup only removes files marked retired in an accepted D1 revision. A stale write cannot reattach a retired file, and a delayed rejection cannot block a newer corrected edit. JSON backups contain metadata and omit cleanup instructions. Retired audio bytes cannot be recovered from a JSON backup.

QA passed 202 Node tests, build and syntax, the Player delete and survivor-only session browser regression, sparse-course ZIP replacement, plus both restore/retirement interleavings using disposable storage. The independent reviewer approved the exact candidate. Once a row contains retirement history, deployment or rollback must use a ledger-aware Worker. The previous Worker cannot read the new tagged envelope.

## 4. Import and sync outcomes

**Scope.** Align ZIP preflight with actual raw and compressed acceptance. Avoid unnecessary buffering and distinguish 413, local durability failure, 409 conflict and transient transport errors. See `SYNC-01` and `SYNC-02`.

**Approach and risk.** Use a shared budget or authoritative server validation to prevent apparently acceptable inputs from diverging at commit. Avoid a duplicate multi-megabyte transfer merely to predict a compressed size. Retain schema and CAS. Permit remote persistence where identity and revision are known even if a local write fails, with accurate feedback about pending durability. Risks include rejecting valid older imports and weakening transient retries or conflict isolation.

**Acceptance.** A compressible library above the old guard imports and reloads. Real raw and stored overages produce actionable recovery, leave the previous accepted snapshot intact and do not retry unchanged. Requests respect bounded reading. Cloud can succeed with IndexedDB unavailable after identity validation. Temporary outage still retries, and two writers still require explicit conflict resolution. Independent Reviewer checks existing SQLite legacy rows, variant sizes and safe failure sequencing.

**Verified locally, 25 November 2026.** ZIP imports use the state API budget. The Worker bounds reads at 16,000,000 request bytes and 1,950,000 encoded row bytes. It reports request, row and record-count limits separately. A rejected save keeps the accepted revision and the pending edits. An unchanged rejected request stays blocked, including across reload. A corrected snapshot can sync after an explicit retry. Device durability and account saving have separate outcomes. IndexedDB failures and stalls no longer prevent an authenticated cloud save or hide export guidance if both stores are unavailable.

Independent QA confirmed a six-lesson ZIP with 2,580 exact cues saved a 3,662,102-byte library and reopened after reload. Bounded chunked requests stopped at the byte limit, real compressed overage preserved the previous revision, and retry plus two writers exercised the 503 and 409 paths. A 24,700,348-byte formatted legacy backup restored and synced, and the browser rejected a 64,000,001-byte backup before reading. Phone recovery notices were inspected in dark and light themes. QA passed 243 Node tests, build, syntax, SQLite compatibility and the current Chromium regressions. The independent reviewer approved after the stale refusal, coherent cache write and stalled write status corrections.

## 6. Measure and bound long-session work

**Scope.** Reduce repeated whole-library network saves during steady playback, bound initial rendering around the active cue, and reduce idle native polling only when existing events preserve intent. See `PERF-01` through `PERF-03`.

**Approach and risk.** Save durable local progress and coalesce the remote snapshot within a defined freshness contract. Use a bounded queue window and avoid repeated full-lesson lookups. Preserve explicit save on transitions, keep de-bounced work verifiable under interruption and never trade away pending seek and phrase-end timing. Risks include missing the current position on reload, regressions when moving across queue windows and callback ordering.

**Acceptance.** Against the 36-lesson, 16,950-cue fixture, target at most one scheduled remote snapshot during 12.6 seconds of uninterrupted playback with intact local progress and deliberate final flush. For the 1,200-cue fixture, mount at most 120 initial rows and target under 100 ms median synchronous opening in the equivalent browser. Verify selection, scroll, focus, retry and conflict. Idle polling improves without affecting timing checks. Independent Reviewer verifies comparable protocol and clock/data regression evidence.

**Verified locally, 25 November 2026.** Playback records an owner-scoped device checkpoint about every five seconds. The first unsent checkpoint starts a 15-second account-save deadline. Ordinary library changes retain their earlier save schedule. Deliberate pause, lesson changes, navigation and completion flush current progress promptly while the page can run. A tab that closes before a network response can recover its last completed device checkpoint after the same owner is verified. After a lost acknowledgement, a verified account can recognise an exact returned copy one revision ahead. Page exit keeps the existing checkpoint when a paused native cursor settles within 30 ms of the saved time on the same cue. Retry, divergent conflicts and capacity rejection retain revision and ownership checks.

On the paired 36-lesson, 16,950-cue fixture, Chromium sent 3 PUTs and 21,383,416 bytes in the 12.6-second baseline. The corrected steady run sent 0 PUTs and had durable progress near 10.15 seconds. Pause saved the current cursor within 0.03 seconds and reload remained paused. At cue 1,171 the queue mounted 80 rows instead of 1,200. Median synchronous opening fell from 228.5 ms to 28.2 ms across seven samples on this runner. Paused native clock reads fell from 101 to 0 in two seconds. Active playback and pending seeks keep their existing timing cadence. Keyboard and touch reached all windows and filtered source ordinals, and Current phrase resumed following after manual browsing.

Independent QA passed 257 Node tests, Worker build and syntax, the scale benchmark, recovery through a synthetic API outage, explicit conflict and transient retry checks, plus current native timing and focus regressions. Mobile and desktop queue captures were inspected. The independent reviewer matched the exact candidate. These measurements use generated media and Chromium on the local runner.
