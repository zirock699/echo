# ECHO-R1 · Performance and reliability

Audited `work` at `923d203f4d303b838cfec64ffc52686fe8f8c335`. The main performance cost in the measured large library was routine progress sync. The phrase queue also slowed substantially when resuming near the end of a long transcript. The small library stayed responsive in this run. Neither finding requires a framework migration.

## PERF-01 · Progress updates retransmit the whole library

**Owner:** performance engineer with data engineer. **Domain:** sync performance. **Severity:** Medium. **Confidence:** high for measured local behavior. **Classification:** design weakness. **Independent validation:** pending.

- **Evidence and cause:** In the 36-lesson fixture, normal continuous listening produced 21.38 MB of request bodies across three saves during 12.6 s. Saves started about 5.02 s apart. `PlayerEngine.tick` calls progress save at roughly five-second intervals during playback. `saveProgress` changes recording position, selected phrase and timestamp through `Store.mutate`; that path persists the full object to IndexedDB. `Store.flush` serializes the full snapshot and writes it to the Worker with the expected revision, then caches it again. Compression in the Worker limits D1 storage size after the browser request. It does not reduce the JSON request body. [Player save cadence](../../../../src/player.mjs#L244), [saveProgress](../../../../src/app.mjs#L242), [Store](../../../../src/store.mjs#L29), [Worker encode/write](../../../../server/worker.mjs#L40).
- **Impact and scope:** Large collections incur bandwidth, serialization and storage work on the core listening path even when only one position changes. This can be costly on constrained uplinks. Local measurements do not establish a particular production slowdown or dropped audio. Confirmed permanent-size handling and the obsolete ZIP cap are tracked separately by the data and architecture lanes.
- **Remediation, effort, risk:** Coalesce progress checkpoints separately from structural writes, preserve prompt local durability, and measure again. If whole snapshots still dominate, add a small revision-checked progress update that can be folded into the same storage model. Keep full saves for structural edits and preserve CAS plus retry/conflict semantics. Estimated 2–4 engineering days including offline/reload/two-client tests. Medium-high risk given persistence and conflict ordering. Depends on the data lane's conflict and cache invariants before changing adapters.
- **Acceptance and regression:** Across the same fixture and playback window, reduce progress-only uploaded bytes per save by at least 90% while keeping progress durable within the agreed checkpoint interval. Track requests, successful revision, and body bytes. Verify reload after an acknowledged checkpoint, interrupted save after a local checkpoint, duplicate retry, interleaved structural edit and stale-device conflict. Preserve local-only progress when the remote update cannot complete. Retain the existing SQLite regression suite.

## PERF-02 · Late resume defeats the queue's row cap

**Owner:** performance engineer with playback and UX. **Domain:** rendering and interaction. **Severity:** Medium. **Confidence:** high. **Classification:** confirmed defect. **Independent validation:** pending.

| Pause position | Synchronous handler median, range | Double RAF median | Queue rows | App elements after open |
| --- | ---: | ---: | ---: | ---: |
| Cue 1 of 60, native CPU | 14 ms (11–18) | 27 ms | 60 | 1,050 |
| Cue 1 of 1,200, native CPU | 45 ms (30–61) | 81 ms | 80 | 4,710 |
| Cue 1,171 of 1,200, native CPU | 167 ms (152–220) | 233 ms | 1,200 | 18,150 |
| Cue 1 of 1,200, CDP 4× | 120 ms (105–171) | 229 ms | 80 | 4,710 |
| Cue 1,171 of 1,200, CDP 4× | 985 ms (770–1,240) | 1,295 ms | 1,200 | 18,150 |

- **Evidence and cause:** Resume a paused native-audio lesson at saved cue 1,171, then open Phrase queue. The nominal 80-row queue starts with a prefix sized to `max(queueLimit, activeIndex + 30)`, so a late cue mounts all 1,200. Rendering each row also performs a fresh linear search over all lesson phrases for its ordinal. The existing lyric node is preserved, but every app render still rekeys and walks all lyric rows, even when the active phrase has not changed. The full-shell replace transplants that node and restores position. [Queue](../../../../src/app.mjs#L117), [render](../../../../src/app.mjs#L190), [queue opening](../../../../src/app.mjs#L329), [lyrics update](../../../../src/lyrics.mjs#L9).
- **Impact and scope:** The slow path occurs during ordinary pause/resume and queue use later in a long track. It makes the queue harder to open precisely when finding an earlier phrase matters. This is distinct from the UX focus loss caused by replacing interactive DOM on progress saves. Existing Library page limits remain effective and should be preserved.
- **Remediation, effort, risk:** Bound the initial queue window near the active cue, with an accessible way to move backward and forward. Precompute ordinals keyed by stable IDs per lesson revision. Skip rekeying or changing unrelated lyric rows when transcript, filter and selected cue are unchanged. Measure results before deciding whether to window the transcript itself. Estimated 1–3 engineering days. Medium risk of altered focus, screen reader order, swipe/scroll or return to the current phrase. Coordinate with the queue and focus repairs to avoid two render-path rewrites.
- **Acceptance and regression:** Late resume opens with the correct active row visible and at most 160 mounted queue rows, with both ends still reachable. Aim for the late-open handler median to be within 25 ms of early open at native CPU on the same 1,200-cue fixture and visibly responsive under 4× emulation. Record five samples for each. Add checks at first/last cues and with filtered selection, keyboard, mobile touch, scroll restoration, and re-open while playing. Keep the real-native timing checks green.

## PERF-03 · Stable paused audio keeps the high-frequency clock loop active

**Owner:** performance engineer with playback engineer. **Domain:** runtime efficiency. **Severity:** Low. **Confidence:** high for native idle tick count, unknown battery impact. **Classification:** technical debt. **Independent validation:** pending.

- **Evidence and cause:** After opening a native lesson, allowing the seek to settle and closing the queue without playback, the 20 ms engine schedule fired 101 callbacks in two seconds in each fixture. A browser wrapper counted the installed interval without changing clock logic. `tick` reads current time and duration, may scan phrases and updates timeline controls even at a stable paused clock. The native adapter already forwards time and seek events. Both playback backends start the high-frequency interval on readiness; pause leaves it running. [Native schedule](../../../../src/player.mjs#L65), [YouTube schedule](../../../../src/player.mjs#L62), [tick](../../../../src/player.mjs#L222), [timeline updates](../../../../src/app.mjs#L227).
- **Impact and scope:** Repeated foreground work while users read or adjust options. No actual battery measurement, hidden-tab claim or accumulating timer leak. One interval is explicitly cleared on relevant destroy/switch paths.
- **Remediation, effort, risk:** Gate the high-frequency loop on playback, seeking or a short recovery state. Use native events for stable paused state and retain bounded polling for API paths without reliable events. Estimated 1–2 days, medium timing risk. Coordinate with playback state-machine fixes before lowering active precision.
- **Acceptance and regression:** In the same two-second stable paused native test, no recurring high-frequency tick should run. Verify first play, pause, deliberately delayed seek, speed and mode changes, manual stop and alternate-source switch with no duplicate loop or changed cue matching. Measure real device power before making a battery improvement claim.

## PERF-04 · The package start entry point cannot start the app on a clean environment

**Owner:** performance engineer with QA. **Domain:** developer reliability. **Severity:** Low. **Confidence:** high. **Classification:** confirmed defect. **Independent validation:** pending.

- **Evidence and cause:** `npm start` in the pristine copy exited 127 with `http-server: not found`. The manifest declares only Color Thief. The advertised command is a static file server and cannot exercise the authenticated API preview; the documented Node dev server starts successfully. [Package scripts](../../../../package.json#L6), [dev server](../../../../scripts/dev.mjs#L8), [README](../../../../README.md).
- **Impact and scope:** A conventional fresh-checkout start fails. Existing documented `npm run dev` works. The Worker build and deployment itself use another path.
- **Remediation, effort, risk:** Point `npm start` at the existing dev entry point or remove the stale alias and keep one documented start path. Default to loopback. Around half a day and low risk. Requires agreement on one supported start command, no runtime dependency.
- **Acceptance and regression:** Use the chosen command on a clean copy. Verify the root HTML, one module with JS content type, and synthetic `GET /api/state`; stop the disposable process. Keep a local Worker build/import check separate from any authorised hosted verification.

## Operational handoff

Keep the existing build and synthetic dev service. Treat offline precache completeness, permanent sync failures and shared deployment controls as separate validation gates tracked by the architect, data and security lanes. Performance priorities are progress checkpoint costs, bounded queue rendering, then paused-loop efficiency after proving clock correctness. There is no evidence here that a backend replacement, package upgrade or an external monitoring service would improve the current app.
