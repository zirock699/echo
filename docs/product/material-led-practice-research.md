# What else can become a useful practice lesson?

25 November 2026 · Product discovery on [`work` at `a3d6a00`](https://github.com/zirock699/echo/commit/a3d6a002cc6cdbbac8ad80c2eee83a38589efa51)

**Test direct import of one audio file and its matching captions first if the learner already uses those pairs.** It takes the same useful principle as the YouTube workflow and applies it to files the learner already has. **Find in transcript** is the stronger first build when that source habit is unknown. It makes long existing lessons easier to revisit without requiring new material.

The original audit found that Echo’s strength was turning a personally chosen recording into exact phrases the learner can hear, repeat and return to. The recent Home correction exposed the library and retired the fixed speaking cards. A proposal in this research starts with actual material or a choice the learner has already made, leads to a specific action, and leaves a clear way to use the result again. [Original product audit](../audits/2026-11-25-923d203/specialists/product-strategist.md) · [Latest roadmap outcome](../transformation/roadmap.md#home-and-practice-correction--25-november-2026)

### Why the first import can stay small

- **Source quality.** An RSS transcript tag can point to plain text or HTML as well as timed SRT, VTT or JSON. A matching edition matters because edits and inserted ads can move speech away from its captions. Check cue bounds and let the learner hear alignment at the first and final cues, and at an interior cue for longer recordings. The initial file route would accept paired SRT/VTT already in hand. Captionless listening is available through ZIP and can be evaluated as a separate loose-file use case. [Podcast transcript specification](https://github.com/Podcastindex-org/podcast-namespace/blob/main/docs/tags/transcript.md) · [WebVTT specification source](https://github.com/w3c/webvtt/blob/gh-pages/index.html)
- **Storage and recovery.** The snapshot validator accepts a native lesson with no YouTube ID and the native adapter can open it. Give it a normal internal lesson ID. The existing Lesson options assume there is a YouTube fallback when removing audio. For a native-only lesson, protect its sole source through explicit replace or lesson removal and offer the video switch only where a valid source exists. Preview local files before uploading. Save through the same owner-checked upload and state path, with existing per-file and snapshot limits, and distinguish a pending device save from a confirmed account save. Cancel, failed decode and account switch must never publish an incomplete lesson. A media upload and its state write are separate, so cancellation, later retirement and owner-scoped cleanup need tests. [Snapshot validator](../../src/snapshot.mjs) · [Native adapter and source selection](../../src/player.mjs) · [Lesson options and removal](../../src/app.mjs) · [Existing import limits](../ZIP_IMPORT.md)
- **Operating cost.** A local file picker and current private storage avoid an additional service, feed integration, scheduled operation or ongoing content catalogue. Automatic podcast and video acquisition would need availability, permissions and matching media versions. YouTube’s official caption method is authorised and has separate listing and download operations. Publisher formats and a playback link alone do not establish rights to import media. [Google’s YouTube API discovery document](https://github.com/googleapis/google-api-go-client/blob/main/youtube/v3/youtube-api.json)

## Tests that could change the order

1. **Import.** Start with two real permitted audio-and-caption pairs the learner already has. Count preparation outside Echo separately, then total time from the ready files to the first correct replay. Compare current ZIP with a thin file-picker prototype on a phone, varying the order. Check the first and final line by ear. The pilot passes if both pairs reach the correct replay faster without archive preparation and the learner chooses the new route for another actual file. At equal preparation effort, keep ZIP as the existing answer. Technical acceptance includes owner change, failed upload or sync, paused open, correct replay and saved position after reload.
2. **Find.** Give the same learner three known words or short expressions across two long lessons, specifying the lesson for each search. Repeat one phrase at several timestamps. Compare time and wrong choices against navigating the current queue ranges. A practical pilot target is correct selection in about half the existing time, with repeat hits distinguishable. Check a long transcript, keyboard focus, an edited phrase and zero results. Exercise Manual and Automatic with a filter active. Typing leaves the playhead, mode, coverage and marks alone. Choosing the result pauses at its cue for deliberate Play.
3. **Review or recall.** Mark two cues from different lessons. On the next visit compare current lesson-by-lesson review with a small derived list. Look for a voluntary return and an improvement in locating the right cue. If the learner wants a speaking measure, take a short first attempt and match equal practice time for two chosen phrases. Try to say one from memory before revealing the model and use ordinary replay for the other. After 24–48 hours, before any replay, try each expression in a different message the learner actually wants to convey. Note whether the expression came to mind or a cue was needed. With a willing listener, check separately whether they got the intended detail on the first hearing. Similar or inconsistent results can leave the current workflow in place.

**Scope decision.** Keep the first change to a single workflow. A static exercise catalogue, automatic transcription, pronunciation scoring, flashcard scheduling, and synced voice recordings carry different content, privacy and support costs. The current evidence favours removing preparation or return friction first. This pass used source review and synthetic probes.
