# Release verification by user journey

T6 turns the existing checks into a repeatable local run. The runner uses only maintained commands and their disposable fixtures. Each browser suite starts its own loopback service, with a generated or synthetic library and a fresh browser context where required. The same shell, application and Worker code remain under test. [Quality and trust](quality-trust.md) · [Runner](../../scripts/verify-journeys.py)

## Reproduce a local run

Use the repository's existing Node and npm setup and Python 3 with Playwright and Chromium. The speech and scale fixtures also use FFmpeg with `flite` and `libmp3lame`. The runner adds no dependencies, build configuration or CI service. Use the existing package commands for an individual Node or build check.

```sh
python3 scripts/verify-journeys.py --list
python3 scripts/verify-journeys.py
python3 scripts/verify-journeys.py --journey start --journey prepare --journey recover
python3 scripts/verify-journeys.py --journey scale
```

Without a selection the full run executes each group in the listed order. It stops at the first failed command, identifies the group and preserves the command's failure exit. `--list` prints commands without executing them. A selected run supplies evidence for its groups only. The runner accepts no site URL or browser profile. The historical Smoke and Extended scripts remain outside the allowlist. [Shared fixture isolation](../../tests/browser_fixture.py)

Before starting, record the source commit and inspect `git status`. Use one clean checkout with the intended candidate and no personal browser state. For a candidate that includes uncommitted edits, record the base and hashes of every reviewed changed or new file. Ensure the independent reviewer verifies the same candidate, with no edits during the run. Record commands, tool versions, exits, fixture, scenarios reached and any traces. Use the isolated fixture account and synthetic content even when testing sign-in changes. Keep private material, access tokens and personalised output out of release evidence.

The browser fixture uses a seven-second default action timeout. A previous concurrent scale run hit action timeouts and then passed in isolation. Leave the original result in the record, note the state reached, and repeat Scale on its own when there is reason to suspect competing work. A repeated same-state failure merits investigation of the app or assertion before changing the budget. The isolated benchmark still measures its own recorded synchronous operations. Neither a blanket timeout increase nor a missing assertion supplies comparable timing evidence. [Scale rerun record](../product/speaking-prompt-handoff.md#local-verification-on-25-november-2026)

List the sizes and states actually observed. Keyboard and accessibility-tree checks supply different evidence from using a screen reader.

## Separate validation gates

Apply each gate to the release changes that reach it. Identify the owner, approved environment or other consent needed before carrying out a check.

| Boundary | Evidence needed |
| --- | --- |
| **Physical phone and assistive technology** | Use a representative device with authorised fixture content. Exercise one-handed Start, Replay, Queue and Exit, actual system Back, orientation and safe areas, browser and text enlargement, interrupted playback and mic refusal/cancel. When the change affects accessibility, include a relevant screen-reader journey. Note device, browser and input method. |
| **Hosted Worker and identity** | Use a specifically authorised disposable account and the intended release environment. Verify actual trusted identity and binding behavior, effective migration and rollback, explicit conflict, owner-switched access and replacement of the full offline shell. Keep hosted results separate from local SQLite and synthetic identity. |
| **Live YouTube or new native reference** | Use an intended, permitted source. Observe visible supported embeds, gesture-gated play, real cue and recovery behavior, including any compact handoff. Verify script, performance and file permissions before trialling a new distributed native take. Record the prepared source and rights status outside personal logs. |
| **Participant outcomes** | With the owner's voluntary participation and agreed handling, compare the present and candidate starts with matched tasks. Track first independently formulated speech, friction, return choice and understanding as different outcomes. Compare equal-time replay with practice and a changed message, then use a later unseen prompt before replay. Record unobserved outcomes as unknown. |

Use a short outcome record per relevant gate. Include the candidate, expected behavior, observed behavior, pass or open status, supporting log or capture, and the evidence owner and independent reviewer. A local green run supports the local acceptance decision. Physical behavior, hosted operation and changes in spoken communication need their own recorded observations.
