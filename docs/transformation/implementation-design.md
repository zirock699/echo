# Echo Studio implementation design

Baseline `work` at `2b9b8fe`. Use the current Home, player and library as the first delivery of the two-start design. The standalone Practice, Library and History prototype remains a comparison for a later navigation decision. The existing Home can already open a speaking cue in one action and reach deliberate Play from a prepared lesson in two. The change tests whether people find the two choices more easily and whether they can apply a reference phrase with fewer steps. Current evidence establishes interaction counts and local behavior. It supplies no measured gain in speaking time, repetition, confidence or unfamiliar-message delivery. ## T1. One useful start and one optional transfer

| State | Presentation and behavior | Acceptance |
| --- | --- | --- |
| Empty verified Home | Put the existing **Try a speaking prompt** first and give it the primary action treatment. One brief description can say that it is a short, fictional update. Keep **Add lessons** visible as the route for bringing a personal reference. | The cue is reachable with one activation, no import and no recording permission. A person with a source can go directly to Add. |
| Populated verified Home | Keep **Resume lesson** first with the same saved lesson, source and location. Put **Try a speaking prompt** next in the reading order, before browsing content. | Two activations through explicit Play. The initial tap opens the saved player paused. Opening a cue requires no selection or library writes. |
| Checking or locked public shell | Keep the existing public prompt available with an actionable account or connection state. Show private artwork, lessons and History only after verification. | A previously cached public shell can display the original text cue. Focus remains stable if account verification settles while the cue is open. |
| Selected phrase in player | Show one named **Try a new conversation** action close to the current phrase, at the boundary with secondary controls. Make it available from a quiet selected phrase, after a completed phrase, in an Automatic speaking wait and when a selected reference is unavailable. Keep Play, Replay and Next dominant. Retain the existing Practice options route. | One activation from the relevant player state, instead of the three-action Settings path. A source may be unready and the text cue still works. The action cannot take focus or apply a mark during recording. |
| No timed phrase | Keep audio-only playback, transport and existing guidance to add a transcript. Offer the original cue from Home. | The phrase-specific entry requires a real selected cue. Captionless audio needs no fake phrase or cue state. |

Use the original bundled E1 situation and the existing distinct E2 transfer prompt. The latter invites the owner to borrow an expression or emphasis and deliver a different message. Cover the chosen reference text while E2 is open. The owner can exit before speaking. An open cue has a single contextual exit, **Back to Home**, **Back to player** or **Back to Practice options**. Back and Escape resolve to the same origin. The two entries stay discoverable after a user closes them. [Existing copy and behavior](../product/speaking-prompt-handoff.md)

Give the named player action at least a 44 CSS px hit area and place it outside the existing swipe target wherever possible. Its visibility must follow the selected phrase and transport intent, with a stable focus target before activation and after close. Disable or defer it while a relevant recorder is acquiring or capturing audio. If the existing exit is what the owner needs, prioritise it over adding another prominent practice tool. No automatic step, audio start, timer or prompt history is needed. Preserve text and gesture use, separate icons for Queue and Compare, and the mini-player's current continuity. At the measured 820 px queue overlap, reserve room for reachable transport or use the existing modal queue behavior with a visible close and correct focus. Do not rely on z-index alone. ## T2. A bounded cue lifecycle

Use one feature-local open/close contract shared by E1 and the two E2 entries. Keep one active cue and one invoking context. The coordinator may own `cue kind`, `invoking surface`, `stable trigger` and `authorised lesson/phrase identity` as transient view state. The existing navigation object owns browser routes, the player owns the clock and adapter, and Store owns progress and recovery. A route may identify a transient overlay for Back and Forward. It carries no response, timed cursor, recording or new persisted practice data. [Architecture assessment](architecture-data.md)

| Event | Required result |
| --- | --- |
| Open E1 from Home | Present the bundled cue and focus its labelled heading. If the existing compact player is active, use the existing pause/checkpoint behavior once. Do not change the chosen lesson or queue. |
| Open E2 from player | Add one temporary sheet entry over the current player route. Pause a wait or pending play using the existing player prompt methods. Preserve the loaded adapter, phrase, cursor, practice mode, queue, selection and scroll. |
| Open E2 from Practice options | Add the cue one level above the existing options sheet. Preserve the active tab, unapplied range or other draft and the original focused action. The Options close path still returns to the underlying player. |
| Pause, late callback or background save | Keep the cue heading and focused control stable. The existing adapter must cancel a pending start and ignore stale events that would resume, advance or write coverage while paused. A background response creates neither a new focused control nor a second modal route. When the player is visible, keep the 200 × 200 full YouTube viewport and native no-video layout. |
| Visible exit, Escape or browser Back | Close exactly one cue. Restore its true invoking surface and focus on the same valid action, with the same scroll and draft. If an authorised item vanished, restore the nearest meaningful surviving control without resurrecting its data. Hold the interrupted source paused until deliberate Echo Play. |
| Browser Forward or reload | Forward within the same live, authorised navigation context can reopen the cue without starting audio. Reload clears the transient cue and keeps private content locked until owner verification. |
| Owner switch or invalid selection | Release the private cue, focus and draft without replaying or exposing the previous owner's metadata. E1 remains a public activity. |

Place the cue in a stable, labelled region so transport, sync, and Library updates can avoid destroying the active element. Reuse the existing focus manager and adapter suspension path, including the stale callback fence, instead of adding a second clock or media controller. During display, make the background inert, hide model text in E2, keep focus within the modal and leave one visible way out. The body may scroll internally. The exit must be reachable by pointer, touch and keyboard without horizontal scrolling. Opening or dismissing a cue changes no Practised/Difficult mark, listening coverage, session count, recording or account preference. Ordinary listened playback before E1 can still checkpoint through the existing Store path. ## T3. Prepare and trust a reference

Keep current input formats, grouping, timestamps, source IDs and rejected-import safety. Clarify the Add route before the user supplies a file. **YouTube lesson** needs a valid link and timestamped text. **Import ZIP** needs a supported prepared archive. Existing private audio attachment still uses Lesson options until separate evidence supports a file-first flow. The initial UX changes can use the present parser and Store.

1. Give **Timestamped transcript** an explicit label pointing to its textarea. Give the separate picker its own **Upload transcript file** label, with supported formats and the chosen filename as accessible description or status. Dynamic labelling must preserve explicit associations. Apply the same contract to **Replace transcript**.
2. Keep entered values, validated file content, optional adjustments and the source after an invalid preview. Give errors their relevant field and move focus to the announced error summary when Preview fails. If content or timing changes, clear stale preview authority while retaining the draft. Keep Save disabled or guarded until a valid preview is current.
3. Use a concise cue count and show the first and final cue bounds among the reviewable lines. Use supplied timing when available and surface estimated ends or uncertainty. A missing or unsupported reference can keep valid text available. Explain repair at the relevant source and preserve the draft on Back within the preview flow.
4. Keep **Save & practise** as one successful transition to the saved, paused lesson. Preserve the originating context and existing Undo for replacement. Native audio can remain playable without a transcript. A timed-text action depends on a chosen cue. YouTube failure offers text and Retry where useful, using the supported embed and no promise of exact edges or captions from a URL.

Treat an authorised, complete short native take as a separate device pilot. Check the exact recording version, both audible edges, replay and interruption, the spoken words, delivery rights and a text fallback. A file-first flow or bundled audio depends on a specific unmet need and passed rights, maintenance and device checks. ## T4. Explain where the work is safe

Store remains the authority on owner identity, cache acknowledgement, conflict and account revision. Derive one current issue with accurate wording and a next action from the relevant saved state. The view supplies no local writer policy. Use the existing floating status outside focused media controls. Dismissing it hides that occurrence, with the data and a route to resolve it still in Settings and Options. Keep any reissued conflict distinguishable by its revision or recovery identity.

| Store outcome | User treatment |
| --- | --- |
| Account accepted or currently saving | **Saved to your account** only after acceptance, or **Saving to your account…** while a write is in flight. When a completed device checkpoint exists, report it distinctly from the account state. |
| Account unreachable and device write confirmed | **Changes are saved on this device.** Supply Retry and retain practice position. |
| Device write failed, durable recovery absent | **Changes are only in this tab.** Offer Retry and the existing export path where relevant. Never recommend closing or switching tabs as safe. |
| Durable pending work from another tab | Offer **Review changes** or the Data team's recoverable handover. Explain whether finishing, reviewing, or continuing read-only is safe. Keep unaccepted changes available to copy, export or review if the selected Store contract can deliver them. |
| Account conflict or rejected update | Show what still exists on each available copy and the existing explicit recovery. A destructive selection describes the pending work it would replace before activation. A quota error points to the part the owner can remedy and keeps the last acknowledged library. |
| Account unverified or owner changed | Keep private data absent and provide the existing verification action. The bundled cue remains available and contains no private metadata. |

Use stable status text rather than announce every playback tick, and keep status below the active prompt in the interaction order. The reproduced same-browser two-tab overwrite is a durability case. Separate browser persistence, in-tab work and account acceptance in both wording and QA fixtures. ## T5. A later worthwhile try

Keep ordinary Home Resume and placement of History. Compare equal-time reference replay with replay plus the distinct original E2 message. On a later visit before replay offer comparable unseen tasks off-app, without requiring a purchase, recording, reminder or health data. Rotate task order, start from an unfamiliar baseline and distinguish voluntary reuse, perceived ease, retrieving the expression and a willing unaware listener's understanding. An unknown result stays unknown. A separate physical phone study observes one-handed transitions, read/exit, permission refusal and interruption using a cleared or owner-supplied source. It establishes device behavior, and the owner comparison establishes what the owner did or experienced.

The smallest optional in-app candidate is one original, bundled **Try a fresh update** entry from the existing History or Home, with one contextual Done or Back and a visible path to Resume. It uses the bounded text cue state, anonymous fiction and no new persistence. It makes no claim that a day elapsed or that the task is intelligently scheduled, and it creates no completion badge. Keep the off-app version preferable if it produces comparable useful practice and the owner already returns easily. New dated exercise records, alerts, a taxonomy and recording need evidence and a separate decision. [Learning methods and evidence](product-learning.md#discovery-sequence-and-decisions)

## T6. Design and release acceptance

| Gate | Required observable outcome |
| --- | --- |
| Start and resume | Empty, populated, checking and locked shells reach the allowed first cue in one deliberate activation. Prepared Home takes two through Play; paused cursor and original source match. Text-only display initiates neither audio nor capture. Check actual rendered wording and hierarchy before claiming discoverability. |
| Direct and nested transfer | Both E2 entry points use one live cue at a time. Compare state before and after open, explicit close, Escape, browser Back and Forward, pause, resize, old source events, background save and owner switch. Verify actual WAV clock, queue and draft, no media restart, exact focused control identity where it remains mounted and no unexpected history or progress. |
| Medium-width player | At 820 × 1180 with Queue open, hit-test Next, Queue, Compare and Play where applicable. On phone check dedicated gestures, reading, selected text and a reachable exit. At desktop use two-column room where it fits. Long phrase, sheet and enlargement remain scrollable inside their intended region. |
| Form and recovery | At 320 × 568, verify the timed-text and file labels separately in the accessibility tree. Invalid preview retains input and focuses the next step. Test failed video with usable text, native captionless and timed routes, paused save, and correct original-source or ZIP interpretation. |
| Private data | Use disposable Chromium with real IndexedDB to force conflicting tab writes, failed saves and same-owner recovery after verification. Every status reflects a completed or explicit Store outcome. Account switch, cached public shell and interrupted retirement protect private data. |
| Presentation and evidence | Use 320 × 568, 390 × 844, 844 × 390, 820 × 1180 and 1440 × 900, light and dark appearances and browser 200% enlargement. Inspect actual captures, contrast, keyboard, touch geometry, native Back and error states. Record device or assistive technology evidence separately when available. |
| Regression floor | Run maintained Node, Worker build/syntax and browser suites against the same candidate. Use current scale fixture for paused clock reads, bounded queue rows and durable checkpoints. Exploration changes have a review gate before hosting, permissions or release. [Quality gates](quality-trust.md) |

A comparison records decisions and actions, voluntary first purposeful speech, errors and return success for equivalent tasks. The delivery target is to preserve the known one- and two-action starts and reduce the transfer path from three actions in Player to one where relevant. Only observed post-implementation results can establish that the path is easier. A prototype, readiness time or simulated decoder provides no participant outcome.
