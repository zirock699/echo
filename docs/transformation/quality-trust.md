# Practice quality and private data

**Assessment base** `work` at `2b9b8fe`, including all eight remediation initiatives and the two speaking prompts. The recommendations below inform the transformation roadmap. Test observations refer to the current local build and disposable data.

## Quality model

The audit and follow-up established a useful maintenance baseline. They restored executable browser checks, repaired data, playback and focus invariants, and separated offline shell availability from private library access. They left the broader product question open. The transformation should assess whether someone can start useful practice, concentrate without interruption, leave safely, and return to the right place even if the screens or routes change. Existing checks provide a credible local foundation. Substantial redesign needs stable outcome assertions and repeatable evidence across the affected journeys, with separate device and hosted gates. ### Make the checks repeatable during AI-assisted changes

1. Give each change an observable contract before implementation. List affected journeys, intended differences, protected outcomes, permitted data and the acceptance commands. Include one pre-change demonstration for a specific regression when it can be reproduced safely.
2. Use the existing fixture to start a fresh service, test identity and profile. Use generated WAV or MP3 for native timing. Use a deterministic adapter for YouTube ordering, controlled storage responses for recovery and the built Worker for packaged routes. Run the scale case without other Chromium work competing for the same machine.
3. Select controls by role and accessible name. Use documented data identifiers only for stable domain identity or geometry that has no suitable semantic locator. Keep network, IndexedDB, actual media, focus and Worker assertions independent of a particular visual layout. Wait for observable completion before reading state. [Playwright locators](https://playwright.dev/python/docs/locators)
4. Record the exact source SHA and changed-file hashes when a candidate includes uncommitted edits. For each check, record command, tool versions, exit code, assertions reached, fixture, viewport, trace location and limits. For a timeout, determine which state the app reached before repeating. Confirm whether changed labels, a replaced render node or machine contention caused a fixture failure before adjusting the test. Preserve the outcome assertion and keep failed runs. Store synthetic traces and screenshots separately from user data. [Playwright Trace Viewer](https://playwright.dev/python/docs/trace-viewer)
5. Before closing, re-run affected checks after any correction and have an independent reviewer match the evidence to the exact candidate. Stop acceptance on wrong-account visibility, lost accepted data, unexpected audio or microphone activity, degraded recovery or an inaccessible required action. State remaining hosted, hardware and learning gaps alongside local results.

**Recommended first investment** is a single documented run list and result format over the existing scripts, followed by a lightweight local runner only if recording and repeat execution take material time. QA and the lead can align the journey map and candidate record in one to two engineering days. Broad screenshot comparisons would create churn during design exploration. Expanding the end-to-end suite for every control would put slower and more fragile checks at the broadest layer. Keep browser journeys sparse and add focused state tests for new failure modes. Consider hosted automation after the manual hosted run is repeatable and suitable synthetic credentials and reversible release targets exist.

**Success** is the ability of a second engineer or agent to rerun the same candidate and explain the same outcome, including preserved pending work, privacy and a reachable exit. During transformation, track evidence by journey and review gate. A large passing count measures execution of existing checks. Journey completion and recovery determine acceptance.

## Security and privacy architecture

Echo has four relevant kinds of data. The bundled shell and original text prompts can be cached independently. Lesson and practice metadata use an owner-scoped IndexedDB copy and revision-checked D1. The media API stores uploaded recordings and artwork under authenticated owner keys and expects a private R2 binding. Microphone attempts are session-only or explicitly saved to a separate owner-scoped device store. A metadata export includes private text and progress. Its scope excludes uploaded media and device attempts. ### Recommended direction and alternatives

Retain managed identity and owner-scoped storage. Make local and bundled practice independent from third-party code, keep capture on-device and reuse validated paths for restores and media changes. This reduces the authority granted by opening the app and removes a dependency for the first-practice path. Estimate one to three engineering days to defer provider loading and verify the affected journeys, once Product and Playback agree on the YouTube and artwork behavior. Confirm the estimate against actual play-gesture behavior in a supported browser. Hosted verification requires an approved isolated site and effective policy access. Target a release record with demonstrated privacy gates and a local entry with zero provider requests.

Preserving eager preparation would keep some video starts fast. It would retain unnecessary provider contact for people opening for a prompt or an uploaded recording. Moving the optional YouTube controller to a dedicated isolated origin could further restrict authority when a video is chosen. It adds deployment, messaging and player compatibility work. Investigate it only if approved lessons rely heavily on embeds and the residual script authority warrants the cost. A local-only application removes server identity and cross-device code, with a corresponding loss of account recovery and web access across devices. Consider that model only if the owner chooses device ownership over those capabilities. A custom authentication or encryption layer adds key, recovery and migration responsibilities to a private single-owner application. Start by proving the existing managed boundary and the user's recovery expectations.

Treat the current hosted verification gap as a release condition, distinct from a confirmed exposure. Confirm account checks, active binding and migration versions, private responses, absence of public bucket exposure, and recovery of synthetic data. Any material increase in sharing, new providers, voice retention or data recipients warrants a new trust-boundary assessment before implementation. OWASP ASVS supplies relevant checks for validation, authorization, browser protections and dependency integrity. The applicable subset follows Echo's actual boundaries.
